# Kit 11: x402 Business Agents (Metal testnet + Airwallex sandbox)

Kit 11 is the second scenario in Atlas. Kit 3 (payment incidents) is still the default; Kit 11 is the second tab on the dashboard (`http://localhost:5173/#kit11`).

**What it shows:** a small data business run by three AI agents (sourcing, support, treasury). Each agent spends under its own capped **Metal mandate**. Every action goes through the Atlas **policy engine**, the **approval queue** and the **hash-chained audit log**. Atlas holds the numbers in code (`server/src/x402/config.ts`); the planner only proposes and explains them.

## The six beats

1. **Mandates.** Policy allows issuing three agent mandates (sourcing cap 0.03 / budget 10, support 0.10 / 4, treasury 1.00 / 6; total 20, which Atlas enforces in code because Metal caps each mandate, not the total). The simulated customer's agent gets its own mandate (cap 0.10, budget 2) that pays only our shop.
2. **Sell queries.** Five queries sold at 0.05. For each, sourcing pays the upstream provider 0.02, then the customer's agent pays us 0.05 with a **signed order** (Metal mandates `requireSignedOffer`), which we store.
3. **Upstream price rise.** Upstream goes to 0.04, above sourcing's 0.03 cap. **Metal refuses** (`mandate_cap_exceeded`), nothing is paid, our shop returns 502, and Atlas checks the facilitator's `/settlements` for the customer's nonce: **customer charged 0.00**.
4. **Human approves new limits.** The treasury agent proposes cap 0.04, budget 10→11 for sourcing, support 4→3 (total stays 20), price 0.06 (keeps a 0.02 margin). Policy **always escalates** a mandate replacement; it would deny a total over 20, a cap above budget, a margin under 0.02 or a cap below the upstream price. After the owner approves, both mandates are replaced on chain (`mandate replace`, spent carried over), the **old credential is refused** (`mandate_revoked`), and Q6 is retried and sold at 0.06.
5. **Dispute & refunds.** The customer disputes Q1–Q4 ("we never placed these, and the data was wrong"). Each signed order is verified against its on-chain payment (`verifyMandatePayment`), proving the customer's agent placed it. Only the orders whose data was stale (Q2, Q4, 30 h old) are refunded from the support mandate. A second refund for Q2 is denied by policy, and replaying the same Metal payment id returns "already paid, nothing sent".
6. **Earnings → Airwallex.** Net = 0.31 revenue − 0.14 upstream − 0.10 refunds = **0.07 \*USDZ**, pulled by the treasury mandate to our off-ramp address, then recorded as a simulated Airwallex sandbox deposit. Paying the EUR licence (invoice `LIC-2026-11`) escalates to the owner; the approval is bound to amount, currency, counterparty and invoice. After approval: USD→EUR FX (SETTLED), then a SWIFT EUR transfer (SCHEDULED).

## Architecture

```
web/src/kit11.tsx          Kit 11 dashboard (beat stepper, feed, approval card, mandates, orders, ledger)
web/src/main.tsx           Kit 3 / Kit 11 switcher (Kit 3 default; #kit11 selects Kit 11)
server/src/x402/config.ts  every price, cap, budget and fee
server/src/x402/metal.ts   MetalConnector interface (one interface, two backends)
server/src/x402/metalTestnet.ts  real Metal testnet via @metalntwx/metal-agent CLI + @metalntwx/metal-pay + @x402/express
server/src/x402/metalSim.ts      labelled in-memory simulation (same semantics: cap, budget, payee, revoke, idempotent pulls, signed orders)
server/src/x402/treasury.ts      Airwallex sandbox deposit / FX / SWIFT (MockTreasury without keys)
server/src/x402/scenario.ts      the six beats; every action → policy → (approval) → connector → audit
server/src/policy/x402.ts        evaluateX402: issue_mandates, purchase, replace_mandates, refund, move_earnings, pay_licence
```

API: `GET /api/x402` (run + config), `POST /api/x402/run` (409 if a run is active), `POST /api/x402/approvals/:id/approve|deny` with `{approver, note}`. Updates stream over the existing SSE endpoint as `event: x402`. Audit events are `x402.*`, connector `metal`, and share the Kit 3 hash chain.

An approval executes at most once: a second click or request for the same approval is rejected while the first is executing.

## How to run

```bash
npm install
npm run dev            # http://localhost:5173 → "Kit 11" tab → Run scenario
```

- **Simulation (no setup):** leave `METAL_RPC_URL` unset. Everything works offline except Airwallex, which falls back to a mock treasury without sandbox keys.
- **Metal testnet:** set `METAL_RPC_URL` in `.env` (a Metal testnet RPC URL; treat it as a secret). Mode defaults to testnet when it is set; force either mode with `METAL_MODE=testnet|simulation`. Wallet and mandate key files are created under `server/.metal/` (gitignored, directories 700, files 600). The business and customer accounts are funded from the self-serve testnet faucet in the `metal-agent` CLI. No Metal console account was needed.
- **Airwallex sandbox:** the existing `AIRWALLEX_CLIENT_ID` / `AIRWALLEX_API_KEY`.
- Headless run (prints every beat and tx hash): `cd server && AUDIT_LOG_PATH=/tmp/x402-audit.jsonl METAL_MODE=testnet npx tsx scripts/x402-run.ts`. Don't run it while the dev server is running a scenario; both use port 4411 for the local seller.

Other knobs: `METAL_SIM_LATENCY_MS` (default 350), `METAL_SELLER_PORT` (4411), `METAL_STATE_DIR`, `X402_PACE_MS` (pause between steps for the UI), `X402_BEAT_HOLD_MS` (how long the dashboard holds each finished beat, default 3000; 0 in tests and the headless script).

A full testnet run takes about 2.5–3.5 minutes (each payment waits for settlement). It spends about 0.21 \*USDZ of the customer's testnet tokens and needs no faucet top-up while balances last.

## Tests

`server/test/x402.test.ts` (17 tests): policy rules for each action, simulated connector semantics (cap, budget, payee, revoke, idempotent pull, signed-order verification), CLI output parsing, the full scenario in simulation, the deny path, at-most-once approval execution and the HTTP routes. CI-style tests never touch the chain.

## Limits

- Testnet only, tokens with no value. Nothing here is mainnet x402.
- Customer and upstream provider are simulated by us.
- Earnings arriving in Airwallex are simulated; the sandbox has no stablecoin on-ramp.
- `@metalntwx/metal-pay` declares Node ≥ 22.13; this was built and run on Node 20.19 without problems, but use Node 22 to match the README.
